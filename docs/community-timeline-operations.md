# Community timeline operations

The public `/timeline` page reads only published records through the server. Platform administrators manage entries at `/admin/community-timeline`. The Firestore default-deny rule blocks direct client access to the `community_timeline` collection; the Admin SDK bypasses rules, so the management API verifies administrator access on every request.

Create a draft, review its wording and source, then mark it approved for publication. Completed entries require a source URL; this check does not verify the source itself. Staff must check original records, dates, claims, image rights, and each external organization's relationship to GO before publishing. Do not publish the proposed July 2022 and April 2023 dates until original records confirm them. Use the reason field to explain publication or corrections. Every save records the previous and new values in `admin_audit_events`. Clear the publication checkbox to withdraw an entry. The public page starts empty; no historical data is seeded or migrated.

The source link may point to an accessible record or an internal reference appropriate for publication. Dates represent the date of the activity or anticipated initiative, not a guarantee of delivery. Describe uncertain initiatives as proposals. Review source links and claims periodically.

No deployment is included in this change. Rollout requires normal application deployment and verification of admin access and public projections against a non-production Firebase project. Roll back the application version to remove the UI and routes; stored entries and audit records remain in Firestore and should be retained for review. Existing Firestore rules already deny direct access to the new collection.

The same admin page maintains the public qualitative hunger panel. Explain the evidence and limitations behind community-interest claims; if referencing Discord, state the participating sample and freshness. Do not describe that signal as a capacity measurement or as the whole community. The review date and changes are audited. The panel has no automatically calculated score.

New GO journey records default to private. Existing records retain their current visibility. Owners can change each log entry's visibility; profile privacy remains an additional boundary. The `GO_DEVELOPMENT_JOURNEY_ENABLED` flag defaults to enabled and can be set to `false` for rollback. No historical backfill is performed. Registration is not attendance: only the organizer's attendance action creates an attendance record, and corrections revoke it. Existing legacy visibility choices are not migrated.

Project, portfolio and learning timeline entries reference existing account, project, CV and enrollment data. They default to private; the owner may share an item only if its source is public, and the profile's privacy boundary is checked independently. Non-game-jam learning registrations and organizer-marked attendance appear separately; game jams use the existing GO development log to avoid duplication. Attendance is shown only while the organizer's record says attended. Portfolio items have no dates in the current CV schema; changes to an item create a new private timeline identity. The timeline reads at most 300 projects, 100 portfolio entries and 100 enrollments. No sensitive membership activation date, eligibility or ballot is projected onto public profiles.

Paid community subscribers may submit suggestions and support approved ideas. New submissions are pending until an administrator opens or rejects them. Administrators can explain status changes, link timeline entries and identify a duplicate's target by ID. A merge keeps the original support count on the original suggestion; it does not transfer or combine supporters, preventing accidental double counting. Audit records retain prior and new moderation values. Treat accepted suggestions as proposals until GO separately confirms a plan.

Administrators create polls with two to ten options and an explicit voting period. Times in the editor use the administrator's local timezone; stored timestamps are UTC. Once a published poll opens its options and dates cannot be edited. Each paid subscriber can cast one ballot per poll. Eligibility is checked again inside the Firestore transaction that creates a deterministic ballot and increments the count. Admins publish results after the close; ties and zero votes are shown explicitly. Polls express informal platform preference and are not statutory association votes or delivery commitments. Ballots are server-only records, not anonymous statutory ballots. The UI currently loads at most 200 suggestions and 100 polls; archive or introduce pagination before exceeding those limits.

Before rollout, verify the full flow in a staging Firebase project, including current paid-through subscription states, two simultaneous votes, result publication, private profiles and source verification. Firestore's default deny protects the new collections and nested ballot/support records; server-side checks remain mandatory because Admin SDK bypasses rules. Existing user records and public development-log choices require no backfill. New community collections and audit records persist if the application is rolled back; avoid deleting them without an approved retention decision. Roll back the application and disable the journey flag if required, then verify that public routes no longer expose new data.
